# The database directory

Postgres is owned by **one service** — `go-data`. Node and Python never
open a connection; they ask Go. That is the reason this directory can
be the single description of the schema rather than one of several.

Paths below are relative to `services/go-data/`, which is where the
service runs from. This file lives in `db/`.

```
schema.sql                THE WHOLE STRUCTURE — idempotent, every boot
migrate.go                the runner
dbcheck/                  drives the guards, rather than inspecting them

db/migrations/*.sql       changes made after schema.sql, applied once each
db/roles.sql              gives myf_client a password, then checks it is safe

db/config.sql             the rows the system cannot work without
db/dump.sql               the practice — 19 clients and their history
db/dump-harness.sql       what the test suites minted; not a fixture
db/make-dump.cjs          regenerates those last two from a live database
db/clear_practice.sql     takes every person back out again

db/SUPABASE.md            moving all of this to a managed database
db/olderDb/               what this replaced: the old schema.sql, the
                          thirty migrations, and fifteen seed scripts
```

## Structure here, rows elsewhere

`schema.sql` contains **no INSERT statements at all**. It describes the
system, not any installation of it — so it can be read as a description
rather than as a snapshot of one laptop, and pushed to a new database
without carrying anything that has happened in this one.

The rows live in three files. Two of them you will actually load, and
the order matters:

```
psql "$DATABASE_URL" -v ON_ERROR_STOP=1 -f db/config.sql   # 1. always
psql "$DATABASE_URL" -v ON_ERROR_STOP=1 -f db/dump.sql     # 2. to have something to look at
```

The third, `dump-harness.sql`, holds the clients the test suites minted
on their way past — "Rereads79zmx4 Testclient" and forty more like it.
Re-running the suites produces them again, so it is kept for
completeness rather than for use.

**`config.sql` first, always.** It holds the country list, the knowledge
base, her weekly hours — the things without which the schema is correct
and the site still cannot take a booking. And `crm.people.country_iso2`
is a foreign key into that list, so a practice loaded into a database
without it is refused on the very first row.

It deliberately does **not** contain `crm.staff`. That row holds a
password hash, and a credential in a repository is a credential. A new
database gets its first officer through the CRM's own setup screen,
which the service refuses once an account exists.

`clear_practice.sql` takes the people back out again and leaves the
configuration. It names every table explicitly and does **not** use
`CASCADE`: if the schema grows a table nobody thought about, Postgres
refuses the whole statement and says which one. Silence is the failure
mode that matters, because nobody re-counts a table they did not know
existed.

**The test suites need the practice.** They are written against Sofia
D'Souza and will fail against an empty database. Load it, run them,
clear it again.

## Why the old files are in olderDb/

The thirty migrations were an accurate record of how one laptop got
from empty to here, and the wrong thing to hand a database that has
never been any of those intermediate shapes. Reading all of them was
the only way to know what the system *is*, which is a bad property for
the only description of it.

The fifteen seed scripts moved with them because `dump.sql` replaces
what they built, and does it from the practice as it actually ended up
rather than from the steps that got there.

`schema.sql` now says that directly, in the order somebody would want
to read it: the visitor, the practice, the person, then row-level
security. Nothing was taken on trust — the rewrite was checked by
building one database from the old migrations and another from the new
file and comparing the catalogs rather than the files: all 340 columns
with their types and defaults, all 127 constraints including the CHECK
bodies, all 113 indexes, all 11 policies with their `USING` and `WITH
CHECK` expressions, which 11 tables have row-level security enabled,
all 194 grants, the trigger and the three functions.

Two differences survive, both deliberate:

- `crm.audit.id` and `crm.bot_turns.id` are now `GENERATED BY DEFAULT AS
  IDENTITY` rather than `serial`. Same behaviour, and the sequence is
  properly owned by the column rather than merely defaulted to.
- `purge_expired_handoffs` schema-qualifies the tables it touches, so it
  no longer depends on `search_path` being what it expects.

The old files stay because they are the only record of *why* several of
those constraints exist. Nothing reads them.

## Changing the schema

Most changes go straight into `schema.sql`: a new table, a new index, a
new column with a default. Every statement there is written to be
harmless the second time, so the change reaches every database on its
next boot.

A **migration** is for what that cannot express — transforming data that
is already there, dropping or renaming something a running installation
depends on, widening a `CHECK` that existing rows would now fail.

Create `db/migrations/NNNN_short_name.sql` with the next number.

- **No `BEGIN`/`COMMIT`** — the runner wraps each file in its own
  transaction, so a failure half way leaves nothing behind.
- Files are **embedded in the binary** (`go:embed`), so a build carries
  its own migrations. A deployment that quietly found no migrations
  would be far worse than one that refused to start. This is also why
  the directory is never empty: `0001_after_the_rewrite.sql` is a
  comment and exists so the embed pattern matches something.
- Filenames are zero-padded so lexical order is numeric order.

Boot order is `schema.sql`, then migrations, oldest first.

## Never edit an applied migration

The runner stores a SHA-256 of every file it applies. If a file it has
already run no longer matches, **the service refuses to start**:

```
[go-data] migrate: migration 0002_x was already applied with
different contents — add a new migration instead of editing this one
```

That is deliberate. A changed migration means the database no longer
matches the file that claims to describe it, and every environment has
drifted differently. The fix is always a new migration.

Note that this does not apply to `schema.sql`, which is not checksummed
and is *meant* to be edited — the price of that is that every statement
in it has to stay idempotent.

## The two guards worth knowing about

```sql
CREATE UNIQUE INDEX appointments_slot_unique
  ON appointments (scheduled_start_at)
  WHERE status IN ('held', 'confirmed');
```

Two visitors shown the same free slot seconds apart will both try to
take it. Everything else — the availability rules, the list of free
times the page was showing — is a snapshot that was true a moment ago.
This index is evaluated at the instant of writing, so it is the only
thing that actually prevents a double booking. Partial, so a cancelled
booking does not keep its hour reserved forever. `crm.consultations`
carries the same index for the same reason.

```sql
CREATE UNIQUE INDEX notifications_once
  ON notifications (appointment_id, kind);
```

Makes a double-clicked Accept fail at the database rather than in
whichever branch of the code forgot to check.

## Checking it

```
DATABASE_URL=... go run ./dbcheck
```

Drives the guards directly rather than inspecting them: two visitors
compete for one slot and the second write must be refused by Postgres,
a cancelled slot must become bookable again, and a second confirmation
for the same appointment must be rejected. Cleans up after itself.
